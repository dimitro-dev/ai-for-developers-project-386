# infra — эксплуатация локального контура

Как поставить Docker-провайдера, поднять контур PostgreSQL, сбросить его данные, запустить мок
контракта, собрать образ приложения и опубликовать его. Правила зоны — в [`AGENTS.md`](AGENTS.md);
архитектурный контур проекта — в [`docs/architecture.md`](../docs/architecture.md).

## Состав контура

```text
infra/
├── compose.yml
├── .env.example
└── postgres/initdb/01-test-database.sh
```

Провайдер — colima + docker CLI + Compose plugin (Homebrew); образ — `postgres:18`, единственный
официальный образ, сборок в самом контуре нет. Имя проекта Compose — `minical`; project directory —
`infra/`, поэтому контур поднимается целями зоны, а не вызовами из корня репозитория.

Образ приложения в контур не входит и в `compose.yml` не описан: он собирается отдельно и живёт
своей жизнью — см. «Образ приложения» ниже.

## Установка Docker-провайдера

Docker нужен для двух вещей — контура базы и образа приложения; обязательный набор проверок
и запуск API и клиента из исходников от него не зависят и работают на машине без него.

На macOS/arm64 провайдер ставится через Homebrew:

```bash
brew install colima docker docker-compose
```

**Обязательный шаг после установки** — без него плагин Compose не находится и любой вызов падает
с «docker: 'compose' is not a docker command»: добавить в `~/.docker/config.json`

```json
{
  "cliPluginsExtraDirs": [
    "/opt/homebrew/lib/docker/cli-plugins"
  ]
}
```

Запуск VM с явно заданными ресурсами:

```bash
colima start --cpu 4 --memory 4 --disk 20
```

Проверка установки:

```bash
docker version
colima status
make -C infra config   # валидирует compose.yml без запуска: плагин Compose найден и конфигурация цела
```

Версии, проверенные 2026-08-16 на этой машине: colima 0.10.3, docker CLI 29.7.2, Docker Compose
5.4.0, Docker Engine (в VM) 29.5.2, образ `postgres:18`.

## PostgreSQL: запуск и остановка

PostgreSQL слушает `localhost:5432`. Цели зоны и их корневые синонимы:

| Из корня | В каталоге зоны | Что делает |
|---|---|---|
| `make db-up` | `make up` | Поднять контур и дождаться healthy |
| `make db-down` | `make down` | Остановить контур, данные сохраняются |
| `make db-logs` | `make logs` | Логи PostgreSQL, follow |
| `make db-reset` | `make reset` | Остановить и **удалить volume** — данные теряются безвозвратно |
| — | `make config` | Проверить конфигурацию compose без запуска |

- **Готовность:** цель подъёма сама дожидается состояния healthy, отдельно ждать не нужно.
- **Порт:** на хосте `5432`, переопределяется `POSTGRES_PORT`; в контейнере всегда `5432`.
- **Базы:** `minical` (разработка) и `minical_test` (проверки `back/002`) — создаются при первом
  запуске на пустом volume.
- **Доступ:** пользователь и пароль по умолчанию — `minical`/`minical`. Полный список переменных
  и их дефолтов — в [`.env.example`](.env.example), переопределяются файлом `infra/.env`
  (в `.gitignore`, наружу не публикуется).
- **`psql` на хосте не нужен** — обращения к базе идут изнутри контейнера:

  <!-- lint-docs: allow-raw — разовый исследовательский запрос к контейнеру, проектной командой не является -->
  ```bash
  docker compose -f infra/compose.yml exec -T postgres psql -U minical -d minical -c "\l"
  ```

- **Только для локальной учебной среды:** пароль по умолчанию слабый, auth в MVP нет, контур наружу
  не публикуется.

## Полный сброс данных

```bash
make db-reset   # контур останавливается, volume с данными удаляется безвозвратно
make db-up      # базы создаются заново пустыми
```

Init-скрипты `/docker-entrypoint-initdb.d/` выполняются **только** при инициализации пустого
каталога данных: на существующем volume правка `postgres/initdb/01-test-database.sh` ничего не
изменит и новая база не появится. Изменение набора баз поэтому требует сброса.

## Мок контракта (Prism)

```bash
make mock
```

Мок-сервер поднимается на `http://localhost:4010` по
`packages/contracts/generated/openapi.yaml`, отвечает на все 12 операций контракта и не требует
backend, PostgreSQL или Docker.

- **Режим валидации:** запрос, не соответствующий контракту (пропущенное обязательное поле,
  нарушение `pattern`, типа и т. п.), отклоняется: если операция документирует 4xx-ответ — им
  (для `POST /bookings` фактически `400`), иначе — сгенерированным `422`; детализация —
  в заголовке `sl-violations`. Конкретный не-2xx ответ можно запросить штатным механизмом Prism:
  `curl -X POST http://localhost:4010/bookings -H "Prefer: code=404" ...`.
- **Дефолтный успешный ответ `POST /bookings` — `200`, а не `201`:** контракт документирует
  у этой операции два успешных статуса (`201` — бронь создана, `200` — идемпотентный повтор),
  а Prism выбирает наименьший 2xx. `201` запрашивается тем же механизмом:
  `curl -X POST http://localhost:4010/bookings -H "Prefer: code=201" ...`. Клиент обязан трактовать
  любой 2xx как успех.
- **Ограничение:** error-тела отдаются сгенерированным примером `{"code":"string","message":"string"}`,
  не соответствующим enum-схемам ошибок; статус выбирается верно, точная форма ошибки — нет.
- **Переключение клиента:** generated SDK (`@minical/api-client`) настраивается на мок через
  `client.setConfig({ baseUrl: 'http://localhost:4010' })`; при готовности backend —
  `baseUrl: 'http://localhost:3001'`. Никаких изменений кода кроме конфигурации base URL
  не требуется.

## Образ приложения

Приложение целиком — один образ: этап сборки экспортирует два web-бандла клиента, рантайм-этап
несёт цепочку API и раздаёт эти бандлы тем же процессом. Второго веб-сервера в образе нет, порт
один.

`Dockerfile` и парный `.dockerignore` лежат **в корне репозитория**, а не в этой зоне: внешняя
проверка учебной платформы собирает образ из корня контекста, и это требование сильнее контракта
размещения. Отступление зафиксировано в [`docs/sources-of-truth.md`](../docs/sources-of-truth.md);
владелец обоих файлов — зона `infra/`.

### Переменные окружения

Набор переменных, их дефолты и дисциплина разбора у образа те же, что у процесса API: читает их
всё тот же `config.ts`. Таблица с допустимыми значениями — в
[`apps/api/README.md`](../apps/api/README.md), раздел «Переменные окружения». Специфика образа
только в том, кто эти значения задаёт:

- **`PORT`** на платформе публикации назначает она сама. Локально его задаёт параметр цели, и он
  же становится портом на хосте: внутри контейнера и снаружи порт один и тот же.
- **`PUBLIC_WEB_URL`** на публикации — выданный платформой адрес сервиса (шаг 2 порядка ниже).
  Локально цель подставляет `http://localhost:<PORT>` вместо дефолта конфига
  (`http://localhost:8081` — адрес dev-сервера Expo): в образе гостевую половину раздаёт тот же
  процесс и живёт она на том же порту, что и API, поэтому дефолт конфига здесь неверен всегда.
- **`SEED_DEMO`** цель пробрасывает только заданным и по умолчанию не передаёт вовсе.

### Локальная сборка и запуск

| Цель | Что делает |
|---|---|
| `make image-build` | Собрать образ из корня репозитория; имя задаётся `IMAGE` (по умолчанию `minical`) |
| `make image-run` | Запустить собранный образ на переднем плане; контейнер удаляется на выходе |

Обе цели принадлежат этой зоне, а в корневом `Makefile` стоят одноимённые делегаты — вызывать
можно и оттуда, и из `infra/`. Переменные окружения передаются параметрами цели:

```bash
make image-run PORT=4321 SEED_DEMO=true PUBLIC_WEB_URL=https://example.onrender.com
```

Контейнер получает имя `minical-<PORT>` — для примера выше это `minical-4321`. Порт в имени
позволяет держать несколько прогонов одновременно; остановить любой из них можно по его имени.
Незаданный `SEED_DEMO` цель не передаёт вовсе: не передать переменную и передать её пустой — для
конфига API разные вещи. Если образ ещё не собран, цель скажет об этом и остановится, а не пойдёт
искать его в реестре.

Что отвечает на выбранном порту:

```text
/         гостевой клиент
/admin    владельческий клиент (без завершающего слэша — редирект на /admin/)
/health   проверка живости
```

Строка запуска живёт только рецептом цели в [`Makefile`](Makefile) этой зоны: сырые вызовы docker
в документации не приживаются — их не пропускает гейт `make lint-docs`.

## Публикация

Платформа — **Render**: собирает образ по `Dockerfile` из корня репозитория, назначает `PORT` сам
и выдаёт публичный HTTPS-адрес `*.onrender.com` без настройки доменов. Адрес известен только после
создания сервиса, поэтому окружение задаётся вторым шагом, а не при создании. Порядок ниже
существенен целиком — каждый шаг опирается на состояние, оставленное предыдущим:

1. **Создать сервис** из репозитория, выбрав сборку по `Dockerfile`. Платформа находит его в корне,
   собирает образ и подставляет свой `PORT`; задавать при создании ничего не нужно.
2. **Задать `PUBLIC_WEB_URL`** выданным адресом сервиса — до его создания адрес неизвестен, поэтому
   шаг только второй; платформа перезапустит сервис сама. Без этой переменной владелец увидит
   в настройках ссылку для гостей `http://localhost:8081` — дефолт локальной разработки.
3. **Проверить сценарий вручную на пустом хранилище:** пройти онбординг на `/admin`, затем
   забронировать слот на `/`.
4. **Включить `SEED_DEMO=true`** — только после проверки.

**Почему сид включается последним.** С включённым сидом онбординг завершён уже на старте, и
повторный `PUT /admin/setup` штатно отвечает `409 ONBOARDING_ALREADY_COMPLETED` — мастер онбординга
на таком инстансе не показать. Проверить его можно единственным способом: на пустом хранилище, то
есть до шага 4. После шага 4 установившееся состояние ссылки — настроенный демо-календарь, где
посетитель по-прежнему заводит типы встреч, меняет настройки и бронирует слоты.

### Что нужно знать про опубликованный инстанс

- **Данные не переживают перезапуск.** Хранилище in-memory: каждый рестарт возвращает ссылку
  к демо-состоянию сида, настройки предыдущего посетителя теряются. Постоянное хранилище появится
  задачей `back/002`.
- **`/admin` публикуется без auth.** Это учебная среда: защиты нет и она не подразумевается —
  правило 9 корневого [`AGENTS.md`](../AGENTS.md) и раздел Security boundary
  в [`docs/architecture.md`](../docs/architecture.md). Путь `/admin` безопасностью не является.
- **Бесплатный инстанс засыпает.** Первый запрос после простоя ждёт холодного старта: «висит и не
  отвечает» здесь не поломка, а разбуженный инстанс.

### Критерий переключения на Railway

Запасная платформа — Railway. Переключение происходит, если бесплатный план Render **не собирает
образ** (лимиты билдера) или **не держит приложение** (память инстанса, политика останова) — то
есть сценарий выше по выданной ссылке не проходится. Отдельного ADR это не требует: решение
и причина фиксируются в `result.md` задачи, а порядок публикации в этом разделе правится
на фактическую платформу.

## Расширение контура

Контур сейчас — один сервис `postgres`. Дальнейшее расширение делается отдельными задачами:

- **`api` и `web`** добавляются задачей вместе с `back/002`: сервисы подключаются к `postgres`
  по параметрам, которые контур уже предоставляет (переменные `POSTGRES_*`, порт, имя базы).
- **Применение миграций** — шаг той же задачи `back/002`; где именно он встаёт (при старте `api`,
  отдельным шагом CI, вручную) — решается там.
- **E2E-прогон web на Playwright (`infra/008`)** поднимает этот же контур как предусловие перед
  тестами; сам контур под эту задачу не меняется.
