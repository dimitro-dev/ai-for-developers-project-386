# Жизненный цикл задач MiniCal

Каждая задача хранится в отдельной директории:

```text
tasks/task-<task-id>/
├── brief.md
├── adr.md
├── plan.md
└── result.md
```

`<task-id>` берётся из постановки пользователя и сохраняется без изменения, например:

```text
tasks/task-000/
tasks/task-002/
tasks/task-BOOKING-003/
```

## Начальная последовательность учебного проекта

| Порядок | Task ID | Назначение | Зависит от |
|---:|---|---|---|
| 0 | [`000`](task-000/) | Подготовить toolchain, generation smoke, Docker-контур и структуру репозитория | — |
| 1 | [`001`](task-001/) | Описать доменные сущности и публичный сценарий гостя | `000` |
| 2 | [`002`](task-002/) | Подготовить продуктовую TypeSpec-спецификацию и generated contract packages | `001` |
| 3 | [`003`](task-003/) | Проверить покрытие сценариев владельца и гостя до реализации | `002` |

Эти задачи не реализуют весь MiniCal. После их завершения отдельно создаются implementation tasks для frontend, backend, database, Slot Engine, Docker runtime и E2E.

## Статус спецификации

Каждый из четырёх файлов начинается с YAML frontmatter:

```yaml
---
status: черновик
---
```

Допустимы только два значения:

```text
черновик
согласовано
```

`status` отражает согласованность самого документа, а не прогресс реализации.

Статус `согласовано` ставится только после явного подтверждения пользователя или назначенного reviewer. Агент может вернуть документ в `черновик`, если обнаружено материальное изменение или противоречие.

Для новой задачи скопируй четыре файла из `tasks/_template/` и замени `<task-id>`.

## Порядок работы

Harness проверяет файлы строго в следующем порядке:

| Порядок | Файл | Назначение | Условие перехода дальше |
|---:|---|---|---|
| 1 | `brief.md` | Продуктовая и техническая постановка, scope, сценарии и acceptance criteria | `status: согласовано` |
| 2 | `adr.md` | Архитектурное решение задачи, последствия и отклонения от общего контура | `status: согласовано` |
| 3 | `plan.md` | Декомпозиция реализации с целью/проблемой, решением и состоянием каждого пункта | `status: согласовано` |
| 4 | `result.md` | Фактический результат, проверки, известные ограничения и описание для MR | `status: согласовано` |

Активным является первый файл со `status: черновик`, у которого все предыдущие файлы согласованы.

Примеры:

```text
brief: черновик
→ уточнять brief; adr/plan/result пока не являются основанием для работы

brief: согласовано, adr: черновик
→ принимать архитектурное решение

brief + adr: согласовано, plan: черновик
→ декомпозировать реализацию

brief + adr + plan: согласовано, result: черновик
→ выполнять пункты plan и формировать result

все согласовано
→ задача завершена
```

## `brief.md`

Минимальные разделы:

```md
# TASK-<id> — Название

## Контекст и проблема
## Цель
## Зависимости
## Пользовательские сценарии
## Функциональные требования
## Нефункциональные требования
## API impact
## Acceptance criteria
## Non-goals
## Связанные документы
```

Brief отвечает на вопрос **что и зачем должно быть сделано**. Он не должен подменяться детальным планом файлов и коммитов.

## `adr.md`

ADR существует внутри каждой задачи. Отдельного глобального каталога ADR нет.

Минимальные разделы:

```md
# Architecture decision

## Контекст
## Решение
## Затронутые компоненты
## Последствия и компромиссы
## Рассмотренные альтернативы
## Совместимость и миграция
```

Если архитектурного изменения нет, файл всё равно заполняется кратко:

```text
Решение: следовать docs/architecture.md без отклонений.
```

Согласованный ADR задачи является решением для её scope. Если он меняет общий архитектурный контур, в plan должен быть пункт обновления `docs/architecture.md` и других затронутых источников правды.

## `plan.md`

Каждый пункт декомпозиции содержит как минимум:

| ID | Цель / проблема | Решение | Состояние |
|---|---|---|---|
| P01 | Что требуется решить | Как это будет реализовано | `в плане` |

Допустимые состояния пунктов:

```text
в плане
выполняется
завершено
```

Правила:

- до начала реализации все пункты находятся `в плане`;
- перед работой над пунктом он переводится в `выполняется`;
- `завершено` ставится только после применимых проверок;
- `status: согласовано` у `plan.md` не меняется при обычном обновлении состояний;
- материальное изменение scope, решения или декомпозиции возвращает `plan.md` в `черновик`.

## `result.md`

Result ведётся во время реализации и становится итоговым отчётом и основой описания MR.

Минимальные разделы:

```md
# Результат TASK-<id>

## Итог
## Что изменено
## Контракт и generated-артефакты
## База данных и миграции
## Выполненные проверки
## Отклонения от brief / ADR / plan
## Известные ограничения и риски
## Описание для MR
```

`result.md` получает `status: согласовано`, когда:

- все обязательные пункты `plan.md` завершены;
- acceptance criteria проверены либо явно отмечены как невыполненные;
- команды и результаты проверок зафиксированы;
- описание MR соответствует фактическому diff;
- результат принят пользователем или ответственным reviewer.

## Возврат к предыдущему этапу

Изменение согласованной спецификации возвращает её в `черновик` и инвалидирует зависимые решения:

| Изменённый файл | Что вернуть в `черновик` |
|---|---|
| `brief.md` | `brief.md`, `adr.md`, `plan.md`, `result.md` |
| `adr.md` | `adr.md`, `plan.md`, `result.md` |
| `plan.md` — материальная декомпозиция | `plan.md`, `result.md` |
| Только фактическое выполнение | обновляется `result.md`; согласованные upstream-файлы не меняются |

Если изменение одной задачи меняет входные условия зависимой задачи:

1. остановить зависимую задачу;
2. зафиксировать ссылку на upstream change;
3. вернуть первый затронутый downstream-файл в `черновик`;
4. продолжить с нового активного этапа.
