# TASK-INFRA-001 — PostgreSQL runtime-контур на Docker Compose

## Контекст и проблема

`docs/architecture.md` фиксирует локальный runtime MiniCal как три контейнера: `web`, `api`, `postgres`. В task-000 этот контур решением пользователя был вынесен в отдельную инфраструктурную задачу, поэтому сейчас проект запускается только напрямую через Node/npm: Expo-клиент собирается на хосте, smoke API работает как локальный процесс на порту 3001, PostgreSQL не запускается нигде.

Реальная ценность контура сейчас — разблокировать Database Agent: схема и миграции требуют работающего PostgreSQL, а установка базы прямо на хост противоречит согласованной архитектуре и не воспроизводится на другой машине. Ревью сузило scope до одного сервиса `postgres` по следующим причинам:

- контейнер `api` оборачивает smoke-сервер, который к базе не подключается — поднимать его в этом контуре нечего ради, кроме факта наличия;
- контейнер `web` дублирует `npm run web` на хосте, а dev-режим с hot reload внутри контейнеров и так вынесен в non-goals — то есть web-образ нужен был бы только для production-like просмотра собранного бандла, которым в учебном проекте никто не пользуется, а каждый `up --build` при этом тянул бы медленный `expo export`;
- оба контейнера — `api` и `web` — добавляются отдельной задачей, когда появится прикладной backend, к которому клиенту и API-контейнеру будет реально нужно подключаться.

Дополнительное ограничение зафиксировано в `../task-000/result.md`: Docker и Docker Compose на macOS-хосте отсутствуют. По правилу task-000 (brief, п. 1) агент не устанавливает обязательный инструмент молча — он предлагает безопасный вариант с обоснованием и действует только после явного подтверждения пользователя. Поэтому установка Docker-провайдера входит в scope этой задачи как отдельный согласуемый шаг.

## Цель

Получить воспроизводимый локальный runtime-контур PostgreSQL на Docker Compose (единственный сервис `postgres`) с healthcheck и env-конфигурацией, в который Database Agent подключается для применения схемы и миграций без пересмотра инфраструктуры. Из чистого checkout контейнер должен подниматься одной документированной командой, а `docker compose config` — проходить без ручного шага копирования `.env`.

## Зависимости

- `000` — monorepo на npm workspaces, корневые npm scripts.
- Docker-провайдер на хосте — отсутствует (см. `../task-000/result.md`). Его установка выполняется только после явного подтверждения пользователя; до подтверждения зависимые пункты плана считаются заблокированными и фиксируются в `plan.md` и `result.md`.
- Задача не зависит от `001`–`003`: контур строится вокруг пустого PostgreSQL, без доменной модели и продуктового контракта.

## Пользовательские сценарии

Продуктовых сценариев нет — задача инфраструктурная. Потребители результата:

- разработчик или агент из чистого checkout выполняет документированную последовательность и получает поднятый `postgres` без ручной донастройки хоста;
- Database Agent получает контейнер PostgreSQL с постоянным volume и подключается к нему по переменным окружения для последующего применения схемы и миграций;
- Backend Agent будущей implementation task, когда появится прикладной backend, подключается к тому же PostgreSQL по переменным окружения; сам backend и его контейнер добавляются отдельной задачей.

## Функциональные требования

1. Проверить наличие Docker Engine и Compose plugin на хосте. При отсутствии — предложить пользователю безопасный вариант установки с обоснованием и выполнить его только после явного подтверждения. Кандидат из ADR task-000 — `colima` + `docker` CLI + `docker compose` plugin через Homebrew: свободная лицензия и тот же CLI-интерфейс, тогда как Docker Desktop и OrbStack имеют коммерческие лицензионные ограничения. Финальный выбор провайдера остаётся за пользователем; фактические версии фиксируются в `result.md`.
2. Подготовить `compose.yml` с единственным сервисом `postgres`: официальный образ PostgreSQL с зафиксированным тегом версии (не `latest`), именованный volume для данных, публикация порта на хост.
3. Настроить healthcheck сервиса `postgres` через `pg_isready`.
4. Вынести конфигурацию в environment. Все переменные в `compose.yml` имеют значения по умолчанию через синтаксис `${VAR:-default}`, поэтому `docker compose config` из чистого checkout проходит без предупреждений о неопределённых переменных и без обязательного шага копирования `.env`. `.env.example` остаётся в репозитории как документация доступных переменных; реальный `.env` игнорируется Git и, если присутствует, лишь переопределяет defaults.
5. Интегрировать контур с корневыми npm scripts: запуск, остановка, логи, полный сброс данных (удаление volume). Существующие команды task-000 продолжают работать без изменений.
6. Обновить README: требования к хосту, установка провайдера, команды запуска/остановки/логов/сброса, занятый порт, переменные окружения, процедура полного сброса состояния, явное предупреждение, что контур предназначен только для локальной учебной среды.
7. Задокументировать точку расширения: как позже в контур добавляются сервис `api`, сервис `web` и шаг применения миграций — без реализации.

## Нефункциональные требования

- Воспроизводимость: контур поднимается из чистого checkout без ручных шагов помимо документированных команд.
- Версия базового образа PostgreSQL зафиксирована конкретным тегом, а не `latest`.
- Данные PostgreSQL сохраняются между `up` и `down` за счёт именованного volume; способ полного сброса состояния (удаление volume) документирован и проверен.
- Конфигурация задаётся только через environment; значения по умолчанию безопасны для локальной среды и не требуют ручного копирования `.env`.
- Образы и Git-история не содержат секретов и реального `.env`.
- Соблюдается security boundary из `docs/architecture.md`: в MVP нет auth, поэтому контур пригоден только для локальной учебной среды и не публикуется наружу.
- Установка Docker-провайдера обратима и не изменяет файлы проекта.

## API impact

`NONE` — TypeSpec-контракт и generated-артефакты не меняются. Контур не содержит прикладного API.

## Acceptance criteria

1. Наличие или установка Docker-провайдера согласованы с пользователем; фактические версии `docker` и Compose plugin зафиксированы в `result.md`.
2. `docker compose config` выполняется из чистого checkout без ошибок и без предупреждений о неопределённых переменных, без ручного создания `.env` (defaults из FR4 покрывают все переменные).
3. `docker compose up` (или эквивалентная документированная команда) из чистого checkout поднимает сервис `postgres` одной командой.
4. Сервис `postgres` достигает состояния healthy (healthcheck `pg_isready` проходит).
5. К PostgreSQL успешно подключается клиент с параметрами по умолчанию из `.env.example`.
6. Данные сохраняются после `docker compose down` и повторного `up` (именованный volume).
7. Документированная процедура полного сброса состояния (удаление volume) выполнена и проверена: после неё контейнер поднимается заново с пустой базой.
8. В образах и в Git нет секретов и реального `.env`; `.env.example` содержит только безопасные значения по умолчанию.
9. README описывает требования к хосту, установку провайдера, команды, занятый порт, переменные окружения, процедуру сброса и предупреждение о локальном назначении контура.
10. Команды task-000 (`npm run generate:check`, `npm run typecheck`, `npm run build`) продолжают проходить на хосте без изменений.
11. Все выполненные команды и результаты проверок зафиксированы в `result.md`.

## Non-goals

- контейнер `api`: smoke-сервис не подключается к базе, поднимать его в этом контуре не имеет прикладного смысла; добавляется отдельной задачей вместе с прикладным backend;
- контейнер `web`: дублирует `npm run web` на хосте, dev-режим с hot reload и так вынесен в non-goals, а собранный бандл в учебном проекте не просматривается production-like; добавляется отдельной задачей вместе с прикладным backend;
- Dockerfile для `apps/api`, Dockerfile для `apps/client`, `.dockerignore` — не требуются: с единственным официальным образом PostgreSQL в контуре нет ни одной сборки образа;
- адрес API для Android Emulator (base URL, gateway-адрес эмулятора) — вопрос клиентской конфигурации и APK, решается в задачах клиента/task-infra-002 и последующих, не относится к контейнеру базы данных;
- прикладной backend: REST-endpoints, бизнес-логика, Slot Engine — отдельные implementation tasks;
- схема PostgreSQL, миграции и seed-данные — задача Database Agent; здесь только пустой контейнер с volume;
- Docker-образ android-builder и сборка APK в контейнере — отдельная инфраструктурная задача (`task-infra-002`);
- production deployment, публикация образов в registry, reverse proxy и TLS, оркестрация;
- auth и любое ограничение доступа к admin;
- CI-пайплайн сборки и публикации образов;
- dev-режим с hot reload внутри контейнеров: Expo dev server и Metro продолжают работать на хосте.
