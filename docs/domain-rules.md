# Domain rules — MiniCal

Этот файл — источник правды для поведения onboarding, расписания, слотов и бронирований. TypeSpec описывает форму API, но не заменяет эти правила.

## 1. Идентичность и доступ

- В системе один заранее заданный владелец календаря.
- Регистрации, login, паролей, токенов, sessions и RBAC нет.
- `ownerId` не принимается от клиента.
- Административные endpoints не защищены и предназначены только для локального учебного запуска.
- Гость не создаёт аккаунт.

## 2. Onboarding владельца

При первом запуске владелец задаёт:

- `displayName`;
- IANA `timeZone`;
- рабочие дни и локальные рабочие интервалы;
- `slotIntervalMinutes`.

Состояние onboarding и настройки хранятся на backend. После завершения onboarding повторный запуск сразу открывает список предстоящих встреч.

Владелец может позднее изменить настройки календаря. Изменения применяются только к будущей генерации слотов.

## 3. Event Type

Минимальные поля:

```text
id
name
description
durationMinutes
```

- `id` задаёт владелец; он уникален и стабилен.
- Backend использует текущую `durationMinutes` для вычисления окончания новой встречи.
- Клиент не передаёт `endAt`.

## 4. Гость и Booking

При создании бронирования гость передаёт:

```text
name — обязательно
email — обязательно
note — необязательно
```

Данные гостя сохраняются как snapshot внутри конкретного Booking. Один и тот же email может иметь несколько бронирований в разное время.

Минимальные данные Booking:

```text
id
eventType reference
startAtUtc
endAtUtc
guestName
guestEmail
guestNote?
createdAtUtc
```

## 5. Рабочее расписание

- Повторяющееся расписание хранится как локальное время плюс IANA timezone владельца.
- Конкретные встречи хранятся как UTC instants.
- Первый UI может разрешать один интервал на день; persistence-модель не должна препятствовать нескольким интервалам в будущем.
- Слот должен целиком помещаться в рабочий интервал.
- Начало слота должно соответствовать `slotIntervalMinutes`.

## 6. Окно записи

Окно состоит ровно из 14 локальных календарных дат в timezone владельца:

```text
today, today + 1, ..., today + 13
```

- Сервер сам вычисляет границы окна.
- Клиент не задаёт произвольные `from` и `to`.
- Слоты, начавшиеся в прошлом, исключаются.
- Встреча должна целиком завершиться в допустимом рабочем интервале и окне.

## 7. Правило занятости

Занятость глобальна для владельца и не зависит от Event Type или гостя.

Два интервала пересекаются, если:

```text
A.start < B.end
AND
B.start < A.end
```

Интервалы трактуются как полуоткрытые:

```text
[startAt, endAt)
```

Допустимо:

```text
10:00–11:00
11:00–11:30
```

Запрещено:

```text
10:00–11:00
10:30–11:00
```

Защита реализуется двумя уровнями:

1. backend повторно проверяет доступность внутри команды создания;
2. PostgreSQL запрещает пересекающиеся активные интервалы constraint-ом.

## 8. Авторитет сервера

- `GET slots` — информационный запрос, а не резервирование.
- `POST booking` заново загружает Event Type, настройки и занятость.
- Backend использует серверное время.
- При конкурентном конфликте возвращается документированная ошибка `SLOT_UNAVAILABLE`.
- Frontend не дублирует Slot Engine как источник истины.

## 9. Изменение настроек

При изменении рабочего расписания или timezone:

- существующие бронирования не удаляются;
- существующие UTC-моменты не сдвигаются;
- новые слоты рассчитываются по новым настройкам;
- существующие бронирования продолжают блокировать своё время.

## 10. Правила, требующие отдельного решения

Не добавлять без отдельной задачи и согласованного `adr.md` этой задачи:

- несколько владельцев;
- auth и удалённая защита admin API;
- исключения по отдельным датам;
- буферы и minimum notice;
- внешние календари;
- отмена и перенос;
- recurring bookings;
- team scheduling.
